# Architecture

[简体中文](../zh-CN/architecture.md) | [Documentation](README.md)

## System Overview

```text
Tauri 2 desktop shell or devicehub-headless browser host
        |
Shared React 19 + Ant Design workspace
        |
Tauri IPC or same-origin URL-fragment bootstrap
        |
Authenticated private loopback WebSocket and HTTP API
        |
Rust / Axum service
        |
idevice: CoreDevice, Lockdown, Installation Proxy, Misagent, Universal HID
```

Vite builds one React UI from `src/`. Tauri embeds those assets and owns desktop lifecycle, while `devicehub-headless` serves the same `dist/` directory without linking Tauri or Wry. `devicehub-host` contains the native file, pairing, FFmpeg, and netmuxd adapters shared by both composition roots.

The accepted [core and runtime extraction](core-runtime.md) evolves this layout into host-independent libraries inside the same repository. Until the migration is complete, the desktop remains the composition root; new code must already follow the documented ownership and dependency direction.

Rust transport adapters should not implement device-control policy independently. The first vertical slice moved to the `application` service layer covers active-session command dispatch, screenshot timeouts, the latest native frame, browser dimensions, and the combined frame version. The HTTP screenshot route and MCP screenshot, input, and frame-wait tools map their formats onto the same `DeviceControlService`; native `watch` notifications or browser-frame broadcasts wake frame waits without adapter-level polling. New capabilities should preserve the dependency direction: transport adapter -> application service -> session capability.

The frontend `useDeviceVideoStream` controller exclusively owns the video WebSocket, WebCodecs decoding, canvas presentation, reconnects, video demand, stall detection, and frontend metrics. `useDeviceInput` independently owns keyboard and pointer listeners, held controls, direct-touch release timers, frame deduplication, and disconnect cleanup; it depends only on the video controller's connection state and narrow command sink, so neither controller invokes the other's lifecycle callbacks. `App` composes those capabilities with page and profile workflows. `useDeviceMediaCapture` separately owns screenshot object URLs, native-screenshot request exclusion, `MediaRecorder`, captured tracks, and unmount cleanup. It receives only the video controller's canvas capabilities and current device context, so capture workflows cannot participate in decoder lifecycle management or retain resources after their workspace ends.

Frontend runtime services follow the same ownership rule. `usePrivateBackend` owns the Tauri bootstrap handshake and bearer-authenticated request construction, while `usePerformanceTelemetry` and `useDeviceLogDemand` own demand activation, polling, and cleanup for their respective supervised services. Device Inspector resources use independent latest-request owners: starting a replacement request or changing the active device aborts the previous fetch and invalidates its state commit, while unrelated backup, sysdiagnose, developer-image, wallpaper, home-screen, WDA, and App-operation requests cannot cancel each other. Non-primary workspaces and large inspectors load through independent React suspense boundaries so the device stage can render without parsing AFC, diagnostics, settings, or mapping-editor code. AFC is loaded only after its first visit and then remains mounted because active transfers and cancellation belong to that workspace lifecycle. `DeviceFullscreenToolbar` owns the separate hardware and function surfaces, pointer capture, and resize observation, while pure `fullscreenToolbarLayout` functions own clamping, nearest-slot snapping, and rendered-bound collision resolution that always keeps the hardware surface authoritative. `App` retains workspace composition and window lifecycle state; persisted device-view preferences independently control the two toolbar docks and Device/Mapping sidebars, and CSS-only Device sidebar collapse preserves active inspector component state.

Key mapping imports pass through a frontend source-adapter registry before entering the existing profile persistence path. Each adapter declares its ID, accepted file types, size limit, parser, and conversion to the shared import result. The UI selects the adapter explicitly, so adding another source does not add format guessing to the profile manager. JSON handles native and scrcpy-mask formats, while a lazy-loaded structured XML parser handles PlayCover `2.0.0` plists. PlayCover imports allow only the standard Apple plist DTD declaration, reject entities, and enforce file-size, nesting, node-count, and model-count limits before converting supported keyboard controls to the shared normalized mapping model. The persisted profile DTO and its validation live in `devicehub-core`. `devicehub-server` owns the profile HTTP adapter over a host-injected `ProfileRepository`, while each host owns durable persistence.

## Desktop and Private Transport

Axum is an internal transport, not a separately deployed web server. It binds a random loopback port by default, has no browser entry point, does not serve the frontend, and requires a per-launch bearer token obtained through Tauri IPC. Device-management routes return `503` when no session is active. There are no private API routes or session commands for IPA parsing, App installation, sideloading, signing, or upgrades; these capabilities are architectural non-goals and must not be introduced by later feature work. Lock, restart, and shutdown commands share a single-flight Diagnostics Relay lease. Lock maps to the one-way sleep request and preserves the parent control session; restart and shutdown allow the device disconnect to end the session.

The WebSocket carries versioned Annex-B HEVC access units and typed control messages. The frontend sends normalized contacts rather than raw HID reports. Rust validates contact identities, the five-contact limit, coordinate ranges, and orientation before dispatch. The Axum route constructs a narrow `WebSocketState`; the real-time transport can access only application status slots, browser frames, clipboard events, video counters, media-demand ports, a device-keyed browser control-lease registry, and the input sink. Each connection owns RAII video and audio demand leases. At most one connection owns input for an exact selection ID, while separate devices remain independently controllable; observers are promoted when the owner disconnects. Disconnect cleanup releases input and media ownership even after an abnormal transport close. JSON/HID validation and bounded WebCodecs ingress flow control are separate modules with no access to HTTP handlers or device-service clients. The shared status projection is also independent of either adapter, so HTTP and WebSocket responses cannot drift while their lifecycles remain separate.

The performance-workbench HTTP routes are a bounded `devicehub-server` adapter. Their dedicated state contains only performance and device-log slots, demand counters, capture and condition status, the service-health registry, and the active-session command sink. The subrouter receives that state before it is merged into the private API, so its handlers cannot extract the broader HTTP application state or reach files, application management, video, clipboard, or profile storage. Protocol-level capture duration validation remains in the adapter, while an asynchronous host capability checks the opaque local destination using desktop or headless filesystem policy. Constructing the adapter only clones lightweight handles and never starts sampling or capture work; those resources remain session-owned and demand-gated.

The bounded device-log buffer, cursor semantics, metadata sanitization, and device-condition observation slot live in `devicehub-core` beside their normalized values. Runtime workers translate Unified Log, syslog, and DVT responses into these ports, but retain demand gating, connection supervision, device clients, and condition commands. Host adapters observe core ports directly and cannot acquire Apple protocol clients through them.

Network capture, Bluetooth capture, backup, sysdiagnose, and log-archive status slots live beside their normalized DTOs in `devicehub-core`. Runtime workers update those host-independent ports while retaining the device clients, command channels, deadlines, and persistence ports. Desktop HTTP adapters therefore observe operation state through core and depend on runtime only when dispatching concrete device work.

Developer Disk Image state, progress, and the iOS-major-version image-type policy also belong to `devicehub-core`. Runtime retains the opaque host asset request, loader port, TSS personalization, image-mounter clients, cancellation, and supervised command worker. The desktop adapter supplies validated local files without exposing paths to core, while future headless hosts can provide the same loader contract.

Backup, sysdiagnose, and Unified Log archive routes form a separate `devicehub-server` diagnostics HTTP adapter. Its state contains only the active-session command sink, the three read-only operation slots, and a host-injected destination preparer. The preparer distinguishes an existing non-root backup directory from replaceable sysdiagnose and log-archive files, then returns only a normalized opaque path. Protocol validation and bounded acknowledgement timeouts live in the adapter, while filesystem inspection, MobileBackup2, DiagnosticsService, and log-stream workers remain host- or session-owned. Constructing or merging this subrouter starts no export, device connection, timer, or polling task, and its handlers cannot access video, application management, performance, clipboard, or profile state.

Application discovery, icons, lifecycle control, uninstall, and bounded console capture use a dedicated application HTTP adapter. Its state contains only the active-session command sink and the shared application-operation progress slot. Bundle identifier validation, response deadlines, and HTTP error mapping stay at this boundary; CoreDevice, DVT, InstallationProxy, and console resources remain session-owned. The adapter cannot access video, files, performance, diagnostics, clipboard, or profile state, and constructing it starts no device work.

Crash-report listing, bounded summaries, export, and deletion use a dedicated crash-report HTTP adapter containing only the active-session command sink. Device-path validation, response deadlines, and summary-only disclosure belong to this boundary, while CrashReportCopyMobile workers and transfers remain session-owned. Constructing the adapter starts no service or transfer and grants no access to unrelated application state.

Device AFC and per-application storage routes use a separate bounded `devicehub-server` HTTP adapter. Its state contains only the active-session command sink and the two scoped transfer-activity slots, so file handlers cannot reach video, application management, performance services, clipboard, or profile storage. Host paths remain opaque adapter values: validation, streaming I/O, rollback, and atomic publication are performed through the runtime's host-injected filesystem port. Transfer workers and AFC clients remain owned by the active device session; constructing or merging this adapter starts no task, connection, or polling loop.

Public AFC and application-container entries, lists, transfer counters, activity state machines, cancellation semantics, bundle-identifier validation, and confined device-path rules belong to `devicehub-core`. `devicehub-runtime` owns only the typed execution commands plus AFC and House Arrest transports, while the host supplies opaque filesystem paths and streaming file I/O. Desktop adapters import storage domain values directly from core instead of relying on runtime compatibility re-exports.

Key-mapping profile routes form a reusable `devicehub-server` adapter with only a host-injected repository port. Profile names, mapping shapes, coordinates, application bindings, and hardware-key conflicts are validated through `devicehub-core` before repository access. The Tauri host alone owns directory selection and asynchronous filesystem persistence. The adapter cannot reach a device session, video, MCP, or supervised services, and constructing it starts no task or watcher.

The MCP service is a separate Streamable HTTP endpoint on `127.0.0.1:8009/mcp` by default. Each protocol connection owns its selected device ID and resolves that session's latest frame, input sink, device state, control channel, performance snapshot, and bounded log buffer from the registry. Automation and the WebView can therefore share an existing CoreDevice session without sharing a mutable target. Changing the MCP target switches only that connection's session-scoped capabilities, not another MCP client or the desktop selection. Performance and log calls acquire temporary demand leases for that device. Coordinate transforms, HID serialization, frame versions, crash-report limits, and identifier policy remain session-scoped. MCP has no authentication; binding it beyond loopback is an explicit deployment decision and emits a warning.

## Session Ownership

The host injects one optional `PairingStore` for both cached Lockdown records used by authenticated Bonjour discovery and RemotePairing identities used by CoreDevice Wi-Fi tunnels. The runtime constructs its private tunnel configuration from that same store, so discovery refresh, Wi-Fi authorization, reconnect, and explicit trust removal cannot observe different credential roots. The desktop implementation owns directories, permissions, file-size limits, and bounded host I/O; no path or credential bytes enter `devicehub-core`. If storage initialization fails, USB discovery remains available while Wi-Fi authorization and credential cleanup return the existing bounded unavailable error.

Device Info reuses its refreshed Lockdown snapshot for normalized identity and regional context. Device class, CPU architecture, model number, and device/enclosure color are limited to short single-line ASCII tokens; they are non-unique descriptive fields and remain separate from UDID, serial number, and ECID identifier policy. Language, locale, time zone, and 12/24-hour preference strings are trimmed, length- and character-validated, grouped into one nullable object, and discarded when no valid field exists. Raw Lockdown dictionaries never cross the private API or MCP boundary.

CoreDevice sessions run on a dedicated Tokio runtime because several `idevice` service objects cannot move safely across a normal `tokio::spawn` boundary. Each session owns its display, HID, AppService, device-state, media, and optional-service resources. Ending or replacing one session cancels only that session's dependent work.

`start_runtime` creates shared manager state, the device-session registry, the dedicated CoreDevice thread, and the outer session manager as one runtime-owned lifecycle. Hosts lazily inject one `RuntimeHostAdapters` capability bundle and receive a `StartedRuntime` containing only the owner and a cloneable `RuntimeClient`; session supervisors, underlying state, owner-future construction, and the manager run loop remain private to `devicehub-runtime`. Device discovery, trust transitions, selection, reconnect, and teardown therefore cannot be reimplemented by a host. `RuntimeClient` separates the manager view from registry-resolved `DeviceSessionClient` values. Device-manager HTTP routes use only the manager view. Device-scoped HTTP middleware requires `X-DeviceHub-Device`, resolves the exact session, and injects its narrow client into the device adapters. WebSocket requires `device_id` and subscribes only to that session's status, media, input, events, metrics, and clipboard. Missing or unknown targets are rejected instead of using frontend selection as an implicit global. The desktop composition root does not implement device routing. Reusable adapters do not read the environment, bind a production listener, or start a device runtime; desktop shutdown stops servers before joining the device owner thread.

The complete authenticated private API route graph now belongs to `devicehub-server`. It assembles status, WebSocket, manager, and device subrouters and verifies the same exact bearer or WebSocket subprotocol token for every route. Tauri supplies the generated token, injected adapter state, desktop CORS layer, listener address, and shutdown lifecycle; it no longer defines route or authentication semantics. A future headless host can therefore reuse the same private API without copying the desktop composition root.

Session media algorithms live behind narrow internal module boundaries. RTP timestamp cadence, Annex-B access-unit assembly, running statistics, decoder restart backoff, and the bounded IRAP-aware HEVC queue own their tests and expose only the operations required by the session loop. A separate RTCP transport module owns peer discovery, receiver statistics, liveness reports, RCTL experiments, and debounced PLI/FIR requests. RTP ingest can only record packets, reset a replaced media source, or submit multiplexed RTCP; it cannot modify RTCP counters or construct feedback packets directly. Neither module owns device clients, decoder processes, or application commands, so transport and orchestration can evolve independently from buffer and feedback policy.

Explicit per-app console capture is isolated in a session-owned supervised worker. It opens fresh AppService and OpenStdioSocket RSD channels, validates the requested installed Bundle ID, binds the returned stdio UUID to an explicit terminating launch, and reads on the CoreDevice `LocalSet`. A sequence-numbered buffer retains at most 1,000 normalized UTF-8 lines and 1 MiB with an 8 KiB per-line limit. Incremental private-API reads detect an expired cursor and return a reset snapshot. Closing the UI clears the buffer; session teardown aborts the stream and clears it unconditionally. Console bytes are never logged, persisted, or registered as an MCP capability.

The Apps view waits only for its core catalog before becoming interactive. Home-screen placement and WDA status are filled in independently in the background. The Apps feature owns its catalog cache, cancellation, request generations, scope selection, and incremental rendering; leaving the view cancels in-flight work, while changing the device or private backend resets the resource. Scope changes are serialized inside the controller so repeated UI events cannot race. Catalogs are cached briefly per device scope and refreshed after device events or mutations. The icon observer fetches only near-viewport assets, avoiding a full Ant Design and icon subtree for large catalogs. Each row receives stable commands instead of parent state setters; memoization isolates it from backup, diagnostics, wallpaper, and other inspector updates. Backup, sysdiagnose, developer-image, and app-operation status use one shared active-task polling policy: the owning tab reads one snapshot on entry, polling starts only while an operation is active, and stops immediately at a terminal state. Request generations prevent a late response from a replaced device or older poll from overwriting current state.

USB Lockdown pairing is a manager-level operation rather than a session input command. Enumeration checks the selected usbmuxd backend for a host pair record and exposes only `paired`, `unpaired`, or `not_applicable`; certificates and record contents never cross the private API. Pairing accepts only an enumerated USB selector and starts only after an explicit desktop action. It waits at most 90 seconds for the device trust dialog, verifies the generated credentials with `StartSession`, adds the UDID only to the serialized host record, and saves it through the same system usbmuxd or bundled netmuxd address. Explicit trust removal uses the same manager boundary and stops only the targeted physical device session. It reads the host ID without exposing it, makes a bounded device-side `Unpair` attempt, and always proceeds to delete the usbmuxd record with one fresh-connection retry plus the in-memory and on-disk Wi-Fi discovery cache and separate RemotePairing identity; results retain whether either side completed so a lost device response is not reported as full success. Unrelated device sessions continue running. Denied, locked, timeout, and generic failures are normalized for the frontend, and logs contain only the device fingerprint. MCP can observe pairing state and receives a transport-specific selection ID so USB and Wi-Fi entries are not conflated, but it cannot trigger or revoke the human trust relationship.

The direct Wi-Fi transport creates RemotePairing credentials only through the explicit USB authorization path and then performs verification-only handshakes over Bonjour. A verification error never starts a replacement pairing or overwrites the saved identity. Short reads, resets, broken pipes, and timeouts retry on fresh sockets before the parent tunnel is rebuilt with a one-to-eight-second bounded exponential delay. A confirmed Pair Verify rejection stops automatic retries and requires explicit USB trust removal and authorization; transient disconnects preserve credentials. Structured logs retain the low-level error class and attempt number, while the public error explains whether to keep the device awake or rebuild authorization.

Optional device services run under a shared supervisor inside a Tokio `LocalSet`. This keeps non-`Send` DVT channel objects on the CoreDevice owner thread while the HTTP, WebSocket, and MCP transports continue using the multi-thread runtime. Each service publishes a common health record with phase, attempt count, restart count, last error, and update time. Location, sysmontap, condition-inducer, graphics, network-monitor, and energy-monitor channels reconnect independently with bounded exponential backoff; one broken channel cannot terminate video or HID.

The normalized service-health record and transition policy live in `devicehub-core`. Each runtime session owns an independent health registry, while desktop and headless hosts observe the same contract. Runtime alone owns reporters, tracing, reconnect backoff, shutdown signals, `LocalSet` tasks, and forced-abort deadlines.

The performance snapshot, typed normalized observations, partial-sample merge semantics, bounded app-activity history, energy target selection, and score normalization live in `devicehub-core`. Runtime converts Sysmontap, DeviceInfo, Graphics, NetworkMonitor, EnergyMonitor, and notification values into that contract while retaining DVT clients, sampling cadence, demand subscriptions, and reconnect supervision. Host adapters read the core observation slot directly and cannot submit raw plist or DVT values.

Location simulation prefers an isolated DVT RemoteServer channel. A bounded DVT connection or channel failure falls back once per supervisor attempt to `com.apple.dt.simulatelocation` over the active `IdeviceProvider`, which supports older developer-image workflows. Both backends share one command queue and normalized `dvt`/`legacy` status, use finite locale-independent coordinate text for the legacy wire format, preserve and replay the current coordinates across backend recovery, and perform bounded clear-on-shutdown cleanup. If both probes fail, the worker enters the normal exponential backoff instead of polling either service continuously.

The supervised Notification Proxy reduces vendor notification names to a fixed event enum. App, disk, name, activation, regional-setting, and Developer Disk Image mount changes refresh only the affected frontend data. Language and time-zone notifications share one `regional_settings_changed` event and are coalesced independently from bursty disk-usage notifications. No vendor payload crosses the boundary; a mount event reports occurrence rather than claiming current state. SpringBoard lock-state changes release all active input and are forwarded without inventing a locked/unlocked value because the notification contains no state payload. MCP consumers use the monotonic event sequence to wait without a read/subscribe race.

Device-detail refresh reads activation state through MobileActivationd in parallel with Lockdown metadata, DiagnosticsRelay AppleSmartBattery data, and AMFI Developer Mode status with a MobileImageMounter fallback. Battery parsing allowlists charge, capacity, electrical, temperature, remaining-time, and adapter-rating fields; numeric values are range-checked, labels are bounded, maximum-capacity percentage takes precedence over the capacity ratio fallback, and serial fields are ignored. The backend reduces activation vendor strings to a fixed public enum and does not request activation records, certificates, or activation-info payloads.

AMFI app-signer trust is an explicit command in the session-owned provisioning worker. In one serialized request, the worker re-queries Misagent, authorizes only a currently installed, parsed, unexpired development profile, then opens a fresh AMFI connection under the same device session. The operation is deadline-bounded and reports success only when AMFI returns a positive status. The frontend requires confirmation; DeviceHub Mask does not install the associated App, and signer trust is not exposed through MCP.

Developer Mode preparation is a separate authenticated command. It opens a fresh paired AMFI service, rechecks the device state, and sends only AMFI action 0 when disabled so the option appears in Settings. It never sends the rebooting enable action or the device-confirmation action. Both the device call and API reply have bounded deadlines.

Device rename accepts only a bounded, non-empty, control-free Unicode name. The session repeats validation, opens paired Lockdown, writes `DeviceName`, and reads the value back before returning success. Diagnostics record only the character count, not the requested name. Lockdown's name-change notification refreshes the device picker and active Info tab. After `StartSession` succeeds, the backend makes a bounded `StopSession` attempt on both rename success and failure. A cleanup error is logged without misreporting a name already accepted by the device as a failed rename.

Device condition simulation owns an isolated DVT Condition Inducer channel and a bounded command queue. The backend bounds and sanitizes the device-provided catalog, and accepts only group/profile pairs from that catalog. Every channel connection first disables any residual condition to establish a known baseline. Apply failures are treated as potentially active because the device may have committed before the reply failed. Session shutdown performs a bounded cleanup; if it cannot confirm success, the shared state retains `cleanup_pending` until a later connection clears the condition. No simulated condition is automatically restored after reconnecting.

Performance monitoring reuses cloned handles to the active software tunnel and creates isolated DVT connections. Sysmontap, graphics, network, and energy sampling are demand-driven by the Performance workspace or selected HUD metrics, and stop when neither needs them. During existing Sysmontap setup, the DVT DeviceInfo hardware response is reduced to logical and physical CPU counts in the range 1–256 and physical-memory capacity in the range 16 MiB–1 TiB; malformed or absent values remain unknown, and no raw hardware dictionary crosses the API. NetworkMonitor uses its own RemoteServer connection; one-second receive/send rates are derived from per-connection counter deltas. Connections expire after one minute without updates and the tracker has a fixed entry limit. The latest normalized snapshot is exposed through the authenticated private API; short-term chart history remains frontend-local and is discarded on device changes. Sysmontap process arrays are decoded against the attribute order negotiated for that session rather than fixed field indices. Per-process CPU is divided by the reported logical CPU count; the snapshot retains the union of the ten highest CPU and ten largest physical-footprint processes, bounded to twenty rows. EnergyMonitor follows at most the first sixteen processes from that bounded list on another RemoteServer connection. It updates the device subscription when the PID set changes, cancels sampling on demand loss, and exposes Apple's relative total, CPU, GPU, networking, display, location, and app-state energy scores. App activity uses a separate DVT Notifications connection that exists only while the Performance workspace requests sampling. Notification types, app or process names, and state values are whitespace-normalized and length-bounded before they reach the private API. The session retains at most 100 events with monotonic sequence numbers, clears them when the device session resets, and never exposes the original archived notification payload.

A separate bounded-queue worker opens DVT DeviceInfo only for an explicit process query. Inventory requests deduplicate PIDs, bound output at 1,024 entries, truncate names to 128 characters, and expose only PID, process/app names, and Apple's application classification through the private API and MCP. MCP status and wait requests accept only a positive PID from a recent snapshot. They reuse one isolated DeviceInfo channel, poll `isRunningPid:` no faster than every 250 ms, and wait at most ten seconds. A running PID may add the sanitized result of `execnameForPid:`; stopped PIDs do not trigger a name query. The worker never calls DeviceInfo directory, UID/GID, or process-control methods, and it never exposes an executable path. A completed wait reports whether the condition was met rather than converting an ordinary timeout into a transport failure.

MCP bundle-state queries use a separate two-item worker and isolated CoreDevice AppService channel, so a wait never occupies HID or the session's management client. Each command accepts one exact, bounded bundle identifier, resolves one user-facing app path, then polls only the process list no faster than every 250 ms for at most ten seconds. The existing direct-parent executable rule is shared with app listing and stop control. Only the bundle identifier plus installed/running booleans cross the boundary; app paths and raw process records remain private.

The session-owned AppService and InstallationProxy listing clients may be closed by the device without a TLS `close_notify`, especially after a Wi-Fi transport transition. A failed read-only app listing discards the required clients, reconnects them with four-second bounds, and retries exactly once before using the existing user-app fallback. App launch first closes the session-owned AppService and prefers a fresh DVT ProcessControl channel, avoiding the CoreDevice `launchapplication` response stall observed on newer iOS builds. CoreDevice AppService is used only when the DVT connection or channel cannot be created before a launch command is sent. Once either backend receives the mutation, a failure or timeout is never replayed automatically because the device may already have committed it. Stop uses one exclusive AppService client. Both commands run as local background tasks with bounded connection, channel, and operation deadlines so a stalled reply cannot block HID or the device-session dispatcher, while a session-local lease rejects concurrent launch/stop races.

Lockdown metadata is read at connection and refreshed for Device Info requests, so push notifications for storage or device-name changes surface current values. App listing and lifecycle control prefer a long-lived CoreDevice AppService client in the same session, avoiding a new RSD tunnel per operation. Process URLs are matched only when their direct parent is the selected app bundle; stop resolves fresh device state and sends a fixed SIGTERM without accepting a client PID or signal. Listing falls back to Installation Proxy when AppService is absent, with running state left unknown. The default scope requests removable user apps only. An explicit system-app scope additionally enables CoreDevice default apps; hidden and internal apps remain excluded. Installation Proxy `Any` only augments those known CoreDevice entries with metadata and is never used to construct a system catalog. If CoreDevice listing fails, the system scope reports that limitation instead of returning an unreliable catalog. The uninstall path still re-queries a single `User` app and never trusts list metadata as authorization. The same bounded Installation Proxy metadata query augments either list path with `StaticDiskUsage` and `DynamicDiskUsage`; values are validated before they cross the private API, and the total is computed with checked arithmetic. Missing or malformed fields remain unknown rather than being reported as zero. App icons use a separate request-driven worker, so icon reads never occupy the HID dispatch loop. It first opens an isolated CoreDevice AppService RSD channel, requests a 64-pixel non-placeholder icon, validates the proprietary dimensions and RGBA byte range, and encodes PNG in memory. A request, transport, or format failure falls back to a separately retained SpringBoardServices channel. Connection failure or timeout disables the CoreDevice source for the current session; two consecutive response or format failures do the same, while a successful icon clears the failure count. The worker then validates PNG headers and dimensions, limits each source and response to 4 MiB, and uses a 256-entry, 32 MiB FIFO cache. The frontend requests only rows near the visible viewport. Home-screen locations use another request-driven SpringBoardServices channel so layout reads cannot delay icon fetches or HID. The parser accepts at most 32 lists, 256 items per list, four folder levels, and 1,024 unique bundle IDs. It returns only app names, bundle IDs, and 1-based ordinal Dock/page/folder routes; an independent three-second channel optionally reads numeric icon metrics bounded to layout dimensions, grid counts, Dock capacity, and page limits. Widgets, smart-stack configuration, Web Clip URLs, and raw plist never cross the private API or MCP boundary. A failed layout request discards the main client before retry, while a failed metrics request leaves the layout result intact. Native screenshots use a separate bounded worker that prefers CoreDevice ScreenCaptureService and falls back to screenshotr through USB Lockdown or the RSD remote shim. The worker accepts one queued request, reuses only a healthy client, validates the PNG and dimensions, and caps the response at 32 MiB; capture never occupies the HID dispatch loop.

App Clips form a second explicit, independently selectable CoreDevice AppService scope. Their `isAppClip` identity survives normalization through the private API and MCP, while the default and Installation Proxy fallback paths always classify entries as regular apps. Stop resolution includes App Clips so a visible running clip can be terminated, but uninstall authorization excludes them because their lifecycle belongs to iOS rather than the traditional installed-user-app path. A requested App Clip scope fails explicitly when AppService is unavailable instead of silently returning an incomplete fallback catalog.

App signing metadata is reduced before it crosses the private API or MCP boundary. First-party and developer classifications prefer CoreDevice flags; bounded Installation Proxy fields then distinguish TestFlight, App Store, generic distribution, or unknown. Generic distribution intentionally combines enterprise and Ad Hoc because signer text alone cannot distinguish them reliably. Only the normalized kind, a validated 32-character numeric minimum-OS version, and the nullable `get-task-allow` boolean are retained. Signer identities, certificate subjects, Team IDs, provisioning UUIDs, and raw entitlement dictionaries are discarded.

Paired Apple Watch discovery uses a separate request-driven CompanionProxy RSD channel over the active iPhone transport. The worker lazily connects, accepts at most two queued commands, returns at most sixteen sanitized registry entries, and discards its client after a failed request so the next query reconnects. Only selected display metadata is read; Watch service startup, control, and port forwarding are outside this boundary. Empty registries are valid, individual metadata values may be absent, and companion identifiers remain sensitive.

WebDriverAgent automation is an on-demand optional service over the active `IdeviceProvider`. It never probes in the background and does not install, sign, or silently launch WDA. An explicit runner start first queries MobileImageMounter for the version-appropriate `Developer` image before XCTest starts; iOS 17 and later use the `Personalized` image type. A definite not-mounted response stops startup with an actionable error, while an unavailable preflight preserves the existing XCTest attempt for compatibility. The refreshed device-details response exposes the same result as a nullable readiness field without returning image signatures or personalization identifiers. MCP commands enter a four-item queue, carry a 12-second deadline, and allow only six selector strategies, 1,024-byte selector expressions, twenty matches, a 1 MiB UI-tree response, 1,024 text characters/4,096 UTF-8 bytes, 100–10,000 ms holds, four fixed scroll directions, and an optional 100–5,000 ms foreground-app restore delay. Device-state reads normalize WDA orientation to a fixed enum and accept only finite positive logical window dimensions up to 100,000 units; lock state and window size are required, while the nonstandard viewport mobile command is optional. Unlock is a separate explicit command with no passcode input and must confirm an unlocked state after WDA returns. App backgrounding targets only the current foreground app and either uses the bounded restore delay or explicitly requests no automatic restore. Element inspection reads only the fixed `type`, `name`, `label`, and `value` attributes plus three boolean states; each primitive text value is limited to 1,024 characters and 4,096 UTF-8 bytes, while arrays and objects are discarded. An element-state wait occupies one serialized worker command, polls no faster than 250 ms, is bounded to ten seconds within the same command deadline, and performs at most one fixed displayed/enabled/selected query per poll after resolving the selected match. Missing elements satisfy only absent/hidden states. Semantic mutations share the global MCP gesture lock. The worker owns one WDA session, resolves element identifiers immediately before each inspection or action, deletes or discards the session after transport failure, and reports `device.wda` health without tearing down display, HID, or management services. Only normalized status, logical device state, bounded XML and attribute scalars, match indexes, finite rectangles, boolean element states, wait summaries, unlock confirmation, background restore policy, and action summaries cross the MCP boundary; text input bodies, WDA session identifiers, element identifiers, and raw geometry payloads remain private.

Manual Developer Disk Image mounting is a separate, explicit supervised task. It accepts only absolute regular local files, rejects symbolic links, bounds the DMG at 1.5 GB and each support file independently. Native-dialog paths cross only the private bearer-authenticated API, while file bytes stay outside the WebView. iOS 16 and earlier require a DMG and signature; iOS 17 and later require a DMG, trust cache, and nonempty `BuildManifest.plist`. Personalized mounting uses idevice's TSS flow and therefore sends device-specific signing identifiers to Apple's service only after the user confirms the operation. The task reports bounded phase/progress state, can be cancelled by the user or session shutdown, and never discovers or downloads images automatically. Explicit unmount uses `/Developer` before iOS 17 and `/System/Developer` on newer systems; it shares the same single-operation queue so mount, unmount, and cancellation cannot race.

Local device backup is an explicit MobileBackup2 worker owned by the active session. USB first uses the lockdown service and can fall back to the cloned RSD tunnel; Wi-Fi uses the remote RSD shim. The host adapter only resolves and validates the native directory selection into a canonical local path; it never receives a MobileBackup2 client, delegate, or device error. The runtime owns protocol execution, disconnect behavior, progress publication, and the confined filesystem delegate. The worker writes only beneath the selected host directory and the validated device identifier. Every delegate filesystem operation verifies lexical confinement and rejects symbolic-link ancestors, including when an existing backup is reused for an incremental run. Progress callbacks publish bounded counters without exposing file paths. Cancellation drops the DeviceLink session immediately and retains already transferred data for a later incremental backup. Restore, erase, backup password changes, and automatic/background backup are outside this boundary.

Sysdiagnose export is a separate explicit CoreDevice DiagnosticsService worker on the cloned RSD tunnel. The request returns after a same-directory temporary file is reserved, while device collection and streaming continue under the session supervisor. The worker runs for at most 45 minutes, accepts at most 8 GiB, rejects oversized chunks or a stream that differs from the device-declared length, and publishes only bounded counters and the selected file name. Cancellation and session shutdown drop the service stream and remove the partial file. Completion flushes and synchronizes the archive before atomically replacing the selected destination; diagnostic contents never cross the private API or MCP boundary.

Device packet capture is a separate, user-initiated pcapd worker. USB sessions first open the traditional lockdown pcapd service and retain the cloned RSD tunnel as a fallback; Wi-Fi sessions use the CoreDevice remote pcapd shim over RSD. An optional PID from the bounded DVT process inventory is captured by value when the operation starts; the worker accepts a packet when either pcapd's primary PID or effective PID matches, counts all other packets as filtered, and never matches the truncated process-name fields. It writes accepted normalized Ethernet records directly to a same-directory temporary host file, caps packets at the negotiated 256 KiB snapshot size and the complete capture at 256 MiB, then atomically replaces the selected `.pcap` destination. Stop, timeout, stream failure, and session shutdown all finalize the writer. Only the selected ephemeral PID, bounded counters, and state reach the private capture API; packet bytes, pcapd process-name fields, and raw pcapd headers never enter WebView or MCP transports.

Bluetooth HCI capture follows the same ownership model around idevice's `BTPacketLogger` stream. It writes big-endian PCAP records using DLT 201 and a four-byte direction pseudo-header, bounds captures to five minutes and 64 MiB, and atomically replaces the selected destination. A missing device-side Bluetooth Logging profile is represented by a valid capture with zero packets, not by inventing an availability result from a silent stream.

Restart and shutdown are separate fixed private-API commands rather than a client-supplied DiagnosticsRelay operation. Each opens an independent relay connection in a bounded task, so waiting for the device acknowledgement does not stall HID dispatch. The frontend requires a device-named confirmation.

App storage uses a dedicated supervised House Arrest worker. USB first attempts House Arrest through the paired Lockdown provider and falls back to a cloned RSD tunnel; Wi-Fi uses RSD only. Every command carries an explicit `documents` or `container` scope and opens a fresh AFC session using `VendDocuments` or `VendContainer`; omitted API scope defaults to Documents for compatibility. Logical paths are rooted at `/Documents` or `/` accordingly and reject traversal and separators in item names. Symbolic links are exposed only as non-actionable special entries. File and directory downloads use rollback-capable local staging, while uploads write a unique remote temporary path and rename it only after every stream closes. Recursive transfers are iterative, limited to 64 levels and 100,000 entries, reject symbolic links and special entries, and verify every regular file's byte count. Uploads do not silently replace an existing item and root mutation is rejected. Recursive deletion requires an explicit API flag, preflights the same depth, entry-type, and symlink constraints, then revalidates each planned item immediately before deleting it in postorder.

The worker publishes a session-scoped transfer activity snapshot for each app. Byte counters are updated while each 64 KiB block is copied and published at most every 100 ms. Single-file transfers expose their known byte total; directory transfers remain indeterminate and report completed bytes, files, and directories without an additional remote preflight traversal. The frontend polls this read-only snapshot only while its upload or download request is active. Cancellation reaches the active transfer through an app- and session-scoped atomic token instead of waiting in the worker queue. Copy loops check it between 64 KiB blocks and directory entries, close open AFC descriptors, and attempt to remove the staged host or device path before reporting `cancelled`.

Public device files use a separate supervised standard-AFC worker. USB first opens `com.apple.afc` through the paired lockdown provider and can fall back to the cloned RSD tunnel; Wi-Fi uses `com.apple.afc.shim.remote` through RSD. AFC2 is never requested. The worker reuses one client until an operation fails, but the private API exposes only bounded operations rooted in that standard AFC container. Paths reject traversal, backslashes, NULs, and unsafe components; symbolic links and special entries are not traversed. File transfer uses 64 KiB buffering and verifies byte counts. Imports stage under a unique remote name and rename only after completion; exports stage beside the selected host target. Recursive transfers are iterative and limited to 64 levels and 100,000 entries. Writes reject name collisions, root mutation, and unsupported local entry types; recursive deletion requires an explicit frontend confirmation. No AFC2 path or MCP mutation crosses this boundary.

The AFC top-level workspace presents four scopes without merging their service or authorization boundaries. Public AFC uses the supervised standard-AFC worker. App Documents and App Container use the existing per-application House Arrest worker after filtering the current app catalog by the scope actually available. Crash Reports uses isolated CrashReportCopyMobile sessions for bounded listing, export, and confirmed single-file deletion. Scope and app selection are locked while one of these operations is active so the owning pane and action state cannot disappear. The public browser only loads a directory while selected and resets when the device changes. Direct path input mirrors the backend's UTF-8 byte and component limits before issuing a request; the backend remains authoritative.

Crash-report list, export, read, and delete operations run in independent Tokio tasks with fresh CrashReportCopyMobile/AFC sessions, so recursive enumeration and file I/O do not block HID dispatch. Listing is bounded by depth and entry count. Export and read revalidate the absolute device path and regular-file metadata and bound allocation to 128 MiB and 1 MiB respectively. Confirmed deletion applies the same path and file-type checks before AFC removal. Desktop summary requests read one selected report on demand with the 1 MiB bound, then serialize only an allowlisted summary: modern IPS JSON and legacy crash headers are recognized while paths, incident IDs, crash keys, stacks, images, and raw termination details are ignored. Raw content remains available only to an explicit bounded MCP read, which includes the same normalized summary; MCP exposes no crash-report mutation tool.

Public AFC imports and exports publish a separate session-scoped activity snapshot. The transfer reuses one 64 KiB buffer across all files and publishes byte and entry counters at most every 100 ms. Single files expose a known byte total; directories stay indeterminate to avoid a second device traversal. The AFC tab polls the snapshot only while its transfer request is active. Cancellation bypasses the serialized AFC command queue through a session-scoped atomic token. Copy loops check it between 64 KiB blocks and directory entries, then discard staged host or device paths before reporting `cancelled`; cancellation does not invalidate an otherwise healthy AFC client.

Clipboard synchronization connects CoreDevice Pasteboard Service only when its persisted opt-in setting is enabled for a newly connected session. Device changes are push-driven when available, while host changes use a bounded-rate poll with echo suppression. The disabled default performs no background clipboard access or transfer; an explicit one-shot paste still writes the requested text. Activity is published through an eight-entry broadcast channel to authenticated WebSocket clients, so UI feedback cannot backpressure the service. One-shot Unicode paste commands share that Pasteboard Service owner through a four-entry command queue and issue Cmd+V only after receiving the SET reply.

App removal uses an independent Tokio task and a fresh Installation Proxy connection so it does not block video, HID, or app-list requests. The backend re-queries an uninstall target and permits only removable, non-first-party user apps. A session-owned single-flight operation state exposes only uninstall stage and device-reported progress.

Device logs use a supervised OsTraceRelay connection only while the log workspace is open. The service exposes structured Unified Log level, process, PID, subsystem, category, and filename metadata. If connecting or starting the Unified Log activity fails, the same supervisor falls back to SyslogRelay; a stream failure triggers a supervised reconnect instead of changing sources inside a live connection. Messages are sanitized and capped at 16 KiB, metadata fields at 512 bytes, before entering a shared 2,000-entry in-memory ring buffer. The private API returns at most 500 entries per poll and reports cursor gaps. Device log content is never forwarded to the application tracing subsystem or persisted automatically.

Offline Unified Log export is a separate explicit OsTraceRelay RSD worker and does not reuse or stop the live stream. It maps the selected 1/6/24-hour window to `StartTime`, requests a 256 MiB device limit, and independently rejects host output above 512 MiB or execution beyond ten minutes. Because the upstream archive API treats socket closure as stream completion, the application also requires nonempty 512-byte-aligned output ending in two zero tar blocks before flushing, synchronizing, and atomically publishing the selected `.tar`. Cancellation and every unsuccessful path drop the service future and delete its same-directory temporary file. Only bounded state, byte count, elapsed time, selected range, and destination file name cross the private API; archive bytes are not exposed to WebView or MCP clients.

A supervised Lockdown heartbeat runs for the lifetime of every active device session. It answers each device `Marco` request with `Polo`, bounds device-provided wait intervals, and reconnects after sleep, timeout, or transport failure. The heartbeat is optional and cannot prevent video, input, or management startup; its lifecycle is exposed through the shared service-health registry.

The native screenshot fallback chain now tries a short-lived DVT Screenshot connection only after CoreDevice ScreenCaptureService and screenshotr both fail, so the additional DDI-dependent path cannot delay either established backend. DVT connection and capture deadlines are independent, its bytes pass through the same format, dimension, and size validation, and a failed DVT attempt is discarded rather than retained in the session worker.

The system-performance supervisor starts the DVT DeviceInfo network-interface query on an independent RemoteServer connection and polls it beside Sysmontap, so a slow or unavailable catalog cannot delay CPU sampling or MCP's first performance sample. Normalization examines at most 256 dictionary entries, retains at most 64 validated ASCII interface names and 96-character descriptions, maps them to a fixed public kind, and exposes an explicit availability and truncation state. IP addresses, MAC addresses, and raw plist values never enter the performance snapshot. Session reset clears the catalog with the rest of the snapshot.

Wallpaper previews share the serialized, request-driven SpringBoardServices home-screen worker. The worker reads the home-screen or lock-screen PNG only after an explicit desktop request, validates its signature and dimensions, limits it to 32 MiB and 16,384 pixels per axis, and returns it with `Cache-Control: no-store`. The WebView holds only a temporary object URL and releases it on close or device change. Wallpaper data is neither persisted nor exposed through MCP, and no wallpaper mutation API is available.

## Video Pipeline

CoreDevice displayservice produces RTP/HEVC. The backend assembles complete HEVC access units into a 16 MiB byte-bounded queue; overflow discards dependent frames until an IRAP and requests PLI/FIR recovery. Rust publishes versioned Annex-B access units over the authenticated WebSocket. The WebView derives the RFC 6381 HEVC profile, tier, level, compatibility flags, and constraints from the SPS, then decodes with `VideoDecoder` and draws `VideoFrame` objects to Canvas. There is no FFmpeg, raw-frame, JPEG, or native video fallback path.

The compressed broadcast buffer absorbs short WebSocket stalls. Broadcast lag, sequence gaps, bounded ingress congestion, decoder backlog, missing output, and configuration changes discard dependent frames and enter an explicit resync state. Transport credit is released only by the matching sequence after the frontend accepts a packet into its bounded decoder ingress queue; presentation acknowledgement is tracked separately for latency telemetry. While resync remains active, the backend suppresses delta frames and retries PLI/FIR until an IRAP is sent. Decoder setup probes exact dimensions and codec and retries progressively simpler `hev1` and `hvc1` configurations. WebCodecs timestamps come from the 90 kHz RTP clock, preserving actual cadence, variable frame rate, and higher refresh rates.

Each WebSocket client explicitly reports whether it needs live video. Only the device page and the live key-mapping background receive frames. Settings, AFC, logs, a static mapping screenshot, and a hidden window keep the RTP/RTCP session alive but stop copying and sending video to that WebView. Resuming display asks for an IRAP before rendering again so decoding does not restart from a dependent P-frame. This gate affects UI display only: MCP screenshots remain available through the on-demand CoreDevice ScreenCaptureService and frame synchronization observes both native and browser frame versions.

Support depends on the platform WebView exposing HEVC through WebCodecs. Windows WebView2 commonly requires the system HEVC Video Extensions; GPU hardware decode support alone does not guarantee that WebCodecs exposes HEVC. An unsupported platform now reports a decoder failure and does not reconnect to a native video decoder. FFmpeg remains isolated to device audio and independent screenshot services remain available to MCP and HTTP clients.

The canvas contain-fits the rotated source with one shared scale. Pointer coordinates are normalized in the exact displayed rectangle, which prevents landscape stretching and touch offset.

## Audio Pipeline

CoreDevice negotiates AAC-ELD at 48 kHz stereo with one 10 ms access unit per RTP packet. The device sends bare access units, so the backend adds RFC 3640 AU headers before forwarding RTP to FFmpeg. FFmpeg decodes to interleaved S16LE and publishes bounded 20 ms PCM chunks to a dedicated native output thread. Rodio converts the stream to the host's default output format. The queue is bounded and stale audio is cleared above 240 ms, so output backpressure cannot delay RTP, video, or input. PCM does not pass through the WebSocket or WebView.

The desktop composition root builds an immutable FFmpeg search plan from its explicit override, packaged resource directory, executable location, and host `PATH`, then injects it through `RuntimeConfig` into each device session. The decoder performs no environment reads and has no global resource-directory state; candidate existence remains lazy so disabled audio does not make FFmpeg a startup requirement.

The same host boundary resolves the optional netmuxd binary, log filter, and upstream usbmuxd address. Runtime discovery receives an immutable sidecar configuration and owns only process supervision; it does not inspect the host environment or executable location.

Settings persistence remains a desktop-host responsibility. The runtime receives a cloneable atomic preference handle containing only session policy; successful host persistence updates that handle, and each new device session snapshots audio and clipboard enablement without knowing a settings file path or format.

Decoded PCM crosses the runtime boundary through a bounded consumer contract. The desktop host supplies the native rodio output and retains playback state, mute, volume, and sound-device recovery; the runtime knows only how to publish fixed-format PCM, allowing a future headless host to select a remote or null consumer without changing device media negotiation.

Audio is off by default. Mute and volume are persisted by the backend and apply directly to native output without depending on browser autoplay policy or page visibility. Output-device failures and runtime decoder exits use bounded retry; a decoder that cannot start drains the negotiated stream without terminating video or input.

## Input Pipeline

Mapping, direct pointer, and keyboard state are combined by the dedicated input controller. Identical touch frames are not resent. Time-dependent mappings use a demand scheduler that starts with the first held mapping key and stops after the last release, blur, disconnect, or unmount; idle input therefore owns no 16 ms interval. Rust converts validated typed contacts into one fixed five-slot Universal HID multitouch report. Keyboard and hardware commands preserve down/up state, and disconnect cleanup releases held usages.

Mapping mode and keyboard passthrough are mutually exclusive. This prevents a single physical key from producing both a mapped touch and a keyboard usage.

## Provisioning Data

Profiles are managed by an independently supervised, bounded Misagent command service, so profile operations do not block the HID input loop. CMS SignedData is decoded before plist metadata enters the private API. Raw profile payloads and provisioned device identifiers never cross into the frontend. A malformed profile is isolated rather than failing the complete result.

Install and removal commands carry request deadlines so a timed-out HTTP request cannot apply later from the queue. Installs validate the local file and profile metadata before device mutation; removals refresh the device catalog before and after mutation. Input, not-found, conflict, transport, and timeout failures retain typed semantics through the private API. Only transport and timeout failures cause the supervisor to rebuild the Misagent channel.

If displayservice is unavailable, the backend preserves a reduced management session when Lockdown remains usable. Screen control and AppService-only actions are explicitly unavailable rather than hiding the whole device.

## Security Boundaries

- The private API remains loopback-only and token-authenticated.
- MCP is loopback-only by default, is unauthenticated, exposes potentially sensitive screenshots, UI trees, process names, device logs, and crash reports, and warns on non-loopback binds.
- Frontend app metadata is never accepted as uninstall authorization.
- HID reports are built only after backend validation.
- Updater artifacts require a Tauri signature before installation.
- Apple Developer ID signing is separate from updater signing.
